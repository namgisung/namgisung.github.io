## TL;DR

수업에서 함수 선언(프로토타입)을 배웠다. 예전에 짰던 8비트 비트시프트 코드가 함수 선언 없이 **함수 정의 순서에 의존**해서 짜여 있었는데, 이번에 배운 걸로 `main` 위에 프로토타입을 올리고 함수 정의는 아래로 내리는 구조로 리팩터링해봤다.

## 예전 코드의 문제

예전에 짠 코드는 이런 순서였다.

```c
int change_byte(int s, int i){ ... }
int left_shift(int s[]){ ... }
int right_shift(int s[]){ ... }
int binary_to_decimal(int s[]){ ... }

int main(void){
    ...
}
```

이게 컴파일이 되는 이유는, C는 함수를 호출하기 **전에 정의(또는 선언)가 먼저 나와야** 하기 때문이다. 그래서 `main`보다 위에 함수 정의를 전부 몰아넣어서 순서를 맞춘 거였다. 문제는:

- `main`이 프로그램의 시작점인데, 코드를 읽을 때는 제일 아래로 내려가야 `main`을 볼 수 있었다.
- 함수가 늘어날수록 `main`을 찾으려면 스크롤을 계속 내려야 하는 구조.

## 배운 것: 함수 선언(프로토타입)

이번에 배운 게, **함수 정의와 함수 선언은 분리할 수 있다**는 거였다. 선언(프로토타입)만 미리 컴파일러에게 알려주면, 실제 정의는 코드 어디에 둬도 상관없다.

```c
int change_byte(int s, int i);
int left_shift(int s[]);
int right_shift(int s[]);
int binary_to_decimal(int s[]);
```

이렇게 함수 이름, 반환형, 매개변수 타입만 적힌 한 줄을 미리 선언해두면, 컴파일러는 "나중에 이런 함수가 정의될 거다"라고 미리 알고 넘어간다. 그래서 실제 함수 몸통(정의)은 `main` 아래로 내려도 아무 문제가 없다.

## 리팩터링

그래서 구조를 이렇게 바꿨다.

```c
#include <stdio.h>
#include <string.h>
#include <math.h>

#define SIZE 8

/* 함수 선언 */
int change_byte(int s, int i);
int left_shift(int s[]);
int right_shift(int s[]);
int binary_to_decimal(int s[]);


int main(void){
    /* ... 기존 로직 그대로 ... */
}


/* 함수 정의는 아래로 */
int change_byte(int s, int i){ ... }
int left_shift(int s[]){ ... }
int right_shift(int s[]){ ... }
int binary_to_decimal(int s[]){ ... }
```

바뀐 건 함수 몸통의 위치뿐이고, `main` 안의 로직(10진수 → 2진수 변환, 좌/우 비트시프트, 다시 10진수로 변환하는 부분)은 그대로다. 그런데도 코드를 읽는 느낌이 확실히 달라졌다.

## 느낀 점

- `main`이 맨 위에 오니까, 파일을 열었을 때 "이 프로그램이 뭘 하는 프로그램인지"가 바로 보인다. 세부 구현(각 함수 몸통)은 궁금할 때만 아래로 내려가서 보면 된다.
- 지금까지는 "함수는 쓰기 전에 정의해야 한다"는 규칙에 맞춰서 코드 순서를 억지로 짰던 거였는데, 선언과 정의를 나눌 수 있다는 걸 알고 나니 **코드 구조를 가독성 기준으로 짤 수 있게** 됐다.
- 헤더 파일(`.h`)에 선언만 모아두고 여러 `.c` 파일에서 나눠 쓰는 것도 결국 이 원리라는 걸 알게 됐다. 다음엔 여러 파일로 나눠서 짜보고 싶다.
